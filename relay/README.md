# PrairieRun iCal relay (Vercel)

A one-file relay the extension publishes its auto-updating iCalendar feed to.
Users subscribe in Apple Calendar / Google Calendar / Outlook with one URL;
every PrairieRun scan overwrites the same feed file, so subscribers stay
current with no OAuth, no Google Cloud project, and no re-invites.

Deploy once per household/organization:

1. Install the Vercel CLI (`npm i -g vercel`) and run `vercel` inside this
   `relay/` directory; link it to one project.
2. Create a Blob store for the project with **public** access — subscribers
   fetch the `.ics` URL directly, so a private store breaks publish (Vercel
   Blob rejects `access: "public"` uploads on private stores):
   `vercel blob create-store <name> --access public --yes` (CLI creates and
   links it, injecting `BLOB_READ_WRITE_TOKEN`), or Vercel dashboard → the
   relay project → **Storage** → **Blob** → create + connect.
   (Live deployment as of 2026-10: project `prairierun-feed` at
   `https://prairierun-feed.vercel.app`.)
3. Generate a publish secret and add it to the project env:
   - `openssl rand -hex 24` (or any long random string)
   - `vercel env add PUBLISH_KEY production` (+ preview/development as needed)
4. `vercel --prod`. Note the deployment URL, e.g. `https://prairierun-relay.vercel.app`.

Then in PrairieRun's **Calendar feed** card on the dashboard page, click
**Sign in with Google** (multi-device) or **Get anonymous feed URL**. The extension
hydrates your feed credentials and shows the stable subscription URL to paste
into any calendar app — no key to type.

## Multi-device Identity (Convex Auth)

To sync a feed URL across multiple devices without separate subscriptions,
PrairieRun pairs this relay with a Convex Auth backend (`convex/`):
- Convex stores the account → `feedId` association (`feeds` table).
- The Convex deployment must have `PUBLISH_KEY` set to the identical value as
  this relay's `PUBLISH_KEY`.
- Convex derives `key = HMAC-SHA256(PUBLISH_KEY, feedId)` on demand for signed-in
  devices, matching the key validation performed by `POST /api/publish`.
- See `convex/README.md` for Convex environment setup.

## Claim endpoint (`GET /api/claim`)

The claim endpoint lets clients mint their own feed with zero dashboard setup.
It requires `PUBLISH_KEY` to be set (same env var as publish) and returns:

```json
{ "ok": true, "feedId": "feed-0123abcd...", "key": "<hex>" }
```

- `key = HMAC-SHA256(PUBLISH_KEY, feedId)` (hex). It only authorizes
  publishing that one `feedId` through `POST /api/publish`; the master
  `PUBLISH_KEY` itself never leaves the server env.
- One claim per client IP per 60s window, tracked in memory per serverless
  instance — a best-effort last-resort limit, not a guarantee.

Notes:

- The feed file lives at `feeds/<feedId>.ics` in Blob storage; the feedId is
  generated by the extension and acts as an unguessable URL secret.
- `POST /api/publish` with header `x-prairierun-key` and body `{ feedId, ics }`
  is the only write path. The header matches either the master `PUBLISH_KEY`
  or the per-feed key `HMAC-SHA256(PUBLISH_KEY, feedId)` for the body's
  `feedId` (minted by `/api/claim` or derived by Convex). It serves permissive CORS so the
  extension page can publish without a host permission (background
  auto-publishes additionally use an optional host permission for the relay).
- Serving HEAD/GET of the blob is handled by Vercel Blob itself; this relay
  has no read endpoint and stores nothing long-term.
